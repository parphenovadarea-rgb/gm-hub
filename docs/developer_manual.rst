Руководство разработчика
========================

Руководство помогает новому разработчику быстро войти в проект: настроить
окружение, запустить программу и тесты, понять устройство кода и принятый
порядок работы.

1. Настройка среды разработки
-----------------------------

1.1. Что понадобится
~~~~~~~~~~~~~~~~~~~~

* Windows 10/11, Python 3.13 (команда ``py``), Git;
* Visual Studio Code (любой редактор подойдёт);
* учётная запись GitHub с доступом к репозиторию
  https://github.com/parphenovadarea-rgb/gm-hub.

1.2. Первый запуск
~~~~~~~~~~~~~~~~~~

.. code-block:: text

   git clone https://github.com/parphenovadarea-rgb/gm-hub.git
   cd gm-hub
   py -m venv .venv
   .venv\Scripts\activate
   pip install -r requirements-dev.txt
   pre-commit install
   py main.py

При первом запуске откроется регистрация (в базе нет пользователей). Чтобы
сразу получить готовые данные, создайте демонстрационную базу отдельным файлом:
``py seed.py demo.db``. Пароль у всех демонстрационных пользователей — ``1234``.

.. warning::

   ``py seed.py`` без аргумента удаляет рабочий ``gm_hub.db``.

2. Устройство проекта
---------------------

.. code-block:: text

   gm_hub/
   ├── config.py, settings.py     пути, форматы, настройки компьютера
   ├── db/                        database.py, schema.sql
   ├── logic/                     правила (auth, games, signups, characters, notes, ...)
   └── ui/                        окна PySide6 (app, common, table, gm_window, ...)
   tests/                         автотесты (unittest)
   docs/                          документация Sphinx
   main.py                        точка входа
   seed.py                        демонстрационные данные

Ключевые точки в коде, с которых стоит начать чтение:

* ``gm_hub/db/schema.sql`` — все таблицы и ограничения (CHECK, UNIQUE);
* ``gm_hub/logic/signups.py`` — самые важные правила: подача и подтверждение
  заявок, лимит мест, очередь;
* ``gm_hub/ui/common.py`` — класс ``MainFrame`` (шапка и вкладки), ``Tab``,
  ``FormGuard`` (защита от потери правок), общие диалоги;
* ``gm_hub/ui/table.py`` — таблица ``RowTable`` с цветными метками и кнопками;
* ``gm_hub/ui/style.py`` — таблица стилей Qt (QSS), в ней весь внешний вид.

3. Порядок работы с кодом
-------------------------

3.1. Git и ветки
~~~~~~~~~~~~~~~~

Используется Feature Branch Workflow: ветка ``main`` содержит только рабочий
код, каждая правка делается в своей ветке (``feature/…``, ``fix/…``) и
попадает в ``main`` через Pull Request на GitHub. Сообщения коммитов — на
русском, одно логическое изменение на коммит.

3.2. Стиль кода
~~~~~~~~~~~~~~~

* форматирование — ``black`` (строки до 88 знаков), проверка — ``flake8``;
  оба запускаются автоматически перед коммитом через ``pre-commit``;
* у каждого модуля, класса и функции — docstring в стиле Google (разделы
  ``Args``, ``Returns``, ``Raises``) на русском: из них собирается документация;
* SQL — только параметризованный; изменения данных — в ``with conn:``;
* логика (``gm_hub.logic``) не импортирует PySide6, а окна (``gm_hub.ui``) не
  содержат SQL.

3.3. Тесты
~~~~~~~~~~

.. code-block:: text

   py -m unittest discover -s tests

Тесты правил работают на БД в памяти (``tests/__init__.py`` содержит
помощники ``make_db`` и ``future``). Тесты окон (``tests/test_ui.py``)
запускаются без экрана (``QT_QPA_PLATFORM=offscreen``). Новая функция логики
должна получить тест, новое окно или клавиша — проверку в ``test_ui.py``.

3.4. Документация
~~~~~~~~~~~~~~~~~

.. code-block:: text

   py -m sphinx -b html docs docs/_build/html

Откройте ``docs/_build/html/index.html``. Страницы руководств лежат в
``docs/*.rst``, справочник API собирается из docstrings, поэтому после
изменения кода достаточно пересобрать документацию.

3.5. Сборка программы
~~~~~~~~~~~~~~~~~~~~~

Команда PyInstaller приведена в разделе :doc:`sysprog_guide` (пункт «Сборка
исполняемого файла»). Перед выдачей сборки проверьте запуск ``.exe`` из
другой папки и открытие окон входа, кабинета Мастера и кабинета Игрока.

4. Как добавить новую возможность
---------------------------------

Пример: новое правило «лимит заявок одного игрока в день».

1. Изменение данных — при необходимости добавьте столбец через
   ``add_column`` в ``gm_hub/db/database.py`` (старые базы обновятся сами) и
   опишите его в ``schema.sql``.
2. Логика — реализуйте проверку в ``gm_hub/logic/signups.py``, при нарушении
   вызывайте ``ValidationError(поле, сообщение)``.
3. Тест — добавьте проверку в ``tests/test_signups.py``.
4. Интерфейс — окно уже ловит ``ValidationError`` и показывает сообщение в
   плашке; если нужно новое поле или кнопка, добавьте их во вкладку
   (``gm_window.py`` или ``player_window.py``) и стиль в ``style.py``.
5. Документация — обновите docstring и страницу ``functionality.rst``.
6. Ветка и Pull Request.

5. Передача знаний новому разработчику
--------------------------------------

Чтобы быстро включиться в проект, новому разработчику нужно:

1. прочитать :doc:`architecture` и :doc:`functionality` (около 15 минут);
2. настроить окружение по разделу 1 и запустить программу на демонстрационных
   данных, пройдя по всем вкладкам обеих ролей;
3. запустить автотесты и убедиться, что все они проходят;
4. открыть ``schema.sql`` и ``logic/signups.py`` — это ядро правил;
5. выбрать из бэклога (:doc:`support`) небольшую задачу с пометкой «минорный»,
   сделать её в отдельной ветке и оформить Pull Request.

Где что искать: техническое задание и отчёт по практике — у автора проекта,
исходный код и история решений — в репозитории GitHub (история коммитов и
закрытые Pull Request), открытые ошибки и планы — в разделе Issues.
